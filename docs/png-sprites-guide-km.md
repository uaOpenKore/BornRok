# PNG-спрайты — руководство для контент-менеджера

Клиент умеет брать спрайты из обычных **PNG-файлов** — без конвертации в .spr/.act и
без спец-инструментов. Прозрачность — обычный альфа-канал PNG (никаких розовых фонов).
Файлы кладутся **рядом с клиентом в папку `data/`** (loose-файлы перекрывают GRF) или
пакуются в zip/GRF — работает одинаково.

Есть два сценария.

---

## Сценарий 1: перерисовать существующий спрайт (в т.ч. в высоком разрешении)

Подходит, когда моб/NPC/шапка уже есть в игре, а надо заменить картинку.

**Что делать:** рядом с виртуальным путём спрайта создать папку с тем же именем и
суффиксом **`.png.d`**, внутрь положить кадры по номерам:

```
data/sprite/몬스터/poring.spr          ← остаётся в GRF, трогать не надо
data/sprite/몬스터/poring.png.d/       ← ваша папка
    0.png
    1.png
    7.png        ← можно заменить не все кадры, остальные возьмутся из .spr
```

- **Номер файла = номер кадра в .spr** (посмотреть кадры и их номера можно в GRF
  Editor / ActEditor: открываете .spr — там кадры идут по порядку с нуля).
- **Высокое разрешение:** PNG может быть в 2/4/8 раз крупнее родного кадра —
  главное, чтобы размер был **кратен** родному (кадр 32×40 → PNG 64×80, 128×160…).
  В игре спрайт останется того же размера, просто станет чётче.
- Анимации, тайминги и точки привязки остаются от родного .act — их трогать не надо.

**Ограничение:** заменённый кадр — полноцветный, поэтому **красители не действуют**
(окраска волос/одежды палитрами .pal работает только на родных кадрах). Для тела и
волос игроков, где важны красители, этот способ не подходит — либо не заменяйте эти
кадры, либо делайте по папке на каждый цвет.

## Сценарий 2: полностью новый спрайт из PNG (новый моб/NPC/эффект)

Ни .spr, ни .act не нужны вообще. Создаёте папку и манифест:

```
data/pngsprite/<имя>/
    manifest.cfg
    idle_0.png
    idle_1.png
    walk_0.png
    ...
```

`<имя>` — то, под которым клиент будет искать спрайт (то же имя, что раньше дали бы
файлу .spr).

### manifest.cfg — пример

```
# Мой новый моб. Строки с # — комментарии.
scale 4              # кадры нарисованы в 4x от игрового размера (хай-рез). Не обязательно.
anchor 32 60         # точка опоры: пиксель кадра (в ИГРОВЫХ пикселях, от левого верхнего
                     # угла), который стоит "на земле между ступней".
                     # Если не указать — берётся низ-центр кадра.

action idle 150      # действие + задержка кадра в миллисекундах
frame idle_0.png
frame idle_1.png

action walk 90
frame walk_0.png
frame walk_1.png

action attack 80
frame atk_0.png
frame atk_1.png sound my_hit.wav    # проиграть звук, когда покажется этот кадр
frame atk_2.png

action hurt 120
frame hurt_0.png

action die 140
frame die_0.png
frame die_1.png
```

### Правила

- **Имена действий:** `idle` (стоит), `walk` (идёт), `attack` (бьёт), `hurt` (получил
  урон), `die` (умирает). Не обязательно делать все — недостающие подменятся первым
  описанным (обычно idle).
- **frame** можно дописать смещение кадра: `frame walk_1.png -2 0` (сдвиг на 2 игровых
  пикселя влево) — если кадр «прыгает» относительно остальных.
- **scale**: если рисуете в 4x — все размеры в манифесте (anchor, смещения) указываются
  в **игровых** пикселях, не в пикселях файла. Размер в игре = размер файла ÷ scale.
- Все кадры одного действия должны быть **одного размера** (так проще держать якорь);
  разные действия могут быть разного размера.
- Пока анимация **одна на все 8 направлений** (моб выглядит одинаково с любой стороны).
  Повороты добавим следующим шагом — раскладка файлов не поменяется.

### Как проверить

1. Положите папку в `data/` рядом с клиентом.
2. Зайдите в игру там, где этот моб/NPC есть (или попросите заспавнить).
3. В логе клиента появится строка `PNG sprite '<имя>' loaded` — значит подхватилось.
   Если что-то не так с манифестом — в логе будет `PNG sprite '<имя>' rejected: <причина>`
   с номером строки.

## Частые вопросы

**Какой размер кадра выбрать?** Ориентир: поринг ~50×50 игровых пикселей, человек
~60×110. Рисуйте в 2–4x от этого и указывайте `scale`.

**Циклится ли анимация?** `walk` и `idle` у мобов циклятся сами; `attack/hurt/die`
проигрываются по разу в нужный момент — клиент управляет этим как у обычных спрайтов.

**Можно перекрыть спрайт из GRF новым PNG-спрайтом?** Да: если есть
`data/pngsprite/<имя>/manifest.cfg`, он приоритетнее .spr/.act с тем же именем.

**Куда класть звук?** Тот же `data/wav/` (или рядом loose) — в манифесте пишется только
имя файла, как в обычных .act-событиях.
