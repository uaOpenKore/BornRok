# Данные из GRF через .lub-скрипты

Клиент управляется таблицами из GRF (скомпилированные `.lub`-скрипты оригинального
клиента), а не хардкод-таблицами в C++ — как в оригинале. Этот документ описывает слой,
что уже подключено, и как проверять его офлайн.

## Зачем

Оригинальный RO-клиент хранит справочные данные (имена спрайтов моб/NPC, тексты
статус-эффектов, id аксессуаров, дерево скиллов и т.д.) в `.lub`-файлах внутри GRF.
`.lub` — это **скомпилированный байткод Lua 5.1** (32-битный, little-endian). Задача —
брать эти данные из GRF в рантайме, чтобы клиент не расходился с сервером/контентом и
не требовал перегенерации при обновлении GRF.

## Как устроено

```
GRF (.lub) ──► Vfs::read ──► GrfData::load ──► LuaTables (Lua 5.1 VM) ──► типизированные lookup'ы
```

- **`third_party/lua51/`** — вендоренная Lua 5.1.5. Патч `lundump.c` позволяет грузить
  32-битный `.lub`-байткод RO на 64-битном хосте (иначе стандартная Lua его отвергает:
  `LoadString` читает 4-байтный размер; `LoadHeader` пропускает ширины int/size_t).
- **`resource/LuaTables.{hpp,cpp}`** — обёртка над одним `lua_State`. Запускает
  `.lub`-чанки, поднимает энумы (`promoteToGlobals`/`aliasGlobal`), читает таблицы
  (`stringMap`, `intKeys`, `intArrayAt`, `descriptRows` — вложенные списки вида
  `{текст,{r,g,b}}`).
- **`resource/GrfData.{hpp,cpp}`** — центральный слой. `load(Reader)` прогоняет цепочку
  зависимых лабов и отдаёт lookup'ы: `npcSpriteName(id)`, `jobSpriteName(id)`,
  `statusDesc(efstId) → {title, body}`.
- Подключён к `Application` (`app.grfData()`), грузится на старте и при ремаунте патчера,
  рядом с `ItemDb`.

## Что уже работает из GRF

| Домен | Источник .lub | Потребитель | Статус |
|-------|---------------|-------------|--------|
| Тексты статус-эффектов (тултип) | `stateicon/efstids.lub` + `stateicon/stateiconinfo.lub` | тултип иконок под миникартой | ✅ |
| Имена спрайтов моб/NPC | `datainfo/npcidentity.lub` + `datainfo/jobname.lub` | рантайм-fallback к сгенерированной таблице | ✅ |

Ключ статус-эффекта в `StateIconList` — это EFST id, он же индекс `SI_` из серверного
пакета `0x196`, так что тултип напрямую индексируется по нему.

## Важные заметки

- **Часть таблиц уже генерируется из лабов на этапе сборки** (`ActorSprites.cpp` из
  `npcidentity.lub`+`jobname.lub`; `AccessorySprites.cpp` из `accessoryid.lub`+`accname.lub`
  через `tools/gen_*.py`). Расхождения с GRF там нет — рантайм-слой лишь *расширяет*
  покрытие (кастомные/новые серверные id, которых нет в baked-таблице).
- **Регистр не важен:** `GrfArchive::normalize` приводит все пути к нижнему регистру, так
  что «Poring» из лаба и `poring.spr` в GRF совпадают.
- **Не все .lub — байткод.** Некоторые (например `datainfo/accname.lub`) лежат как
  **исходник** (начинается с `--[[`). Исходники с CP949-строками могут падать на байте
  `0x5C` (трейл-байт CP949, который лексер Lua принимает за escape → «unfinished string»).
  Байткод-лабы этой проблемы лишены. Нужные сейчас лабы — байткод и грузятся чисто.

## Пока не переведено на GRF (осознанно)

- **Спрайты тела игрока** — `pcJobTbl2` отдаёт числа, а не имена (лабиринт идентичности).
  Оставлен рабочий хардкод `jobSpriteName` в `CharacterActor.cpp`.
- **Дерево скиллов** (серые невыученные) — `skilltreeview.lub` требует player-центричный
  `JOBID`, которого нет в NPC-таблице `jobtbl`. Берём из серверного `db/skill_tree.txt`.
- **`.str` / partical-эффекты** (движок `effecttoolutil.lub`) — большая отдельная фича,
  не таблица данных.

## Проверка офлайн

Инструмент `grflub` грузит `GrfData` через тот же путь чтения, что и игра
(`GrfArchive.read`), и печатает результат — без bgfx/SDL-сборки клиента:

```
grflub <archive.grf>                 сводка + примеры
grflub <archive.grf> status [id...]  тексты статус-эффектов (EFST)
grflub <archive.grf> mob [id...]     имена спрайтов моб/NPC по class id
```

Сборка (core-пресет): `cmake --build build/core --target grflub`.

Пример: `grflub data.grf status 1 10 110` → Endure / Blessing / Assumptio с описаниями.
