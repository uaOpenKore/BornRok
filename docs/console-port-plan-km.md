# План порта uaRO на консоли (PS5 / Xbox / Nintendo Switch)

Цель: **подготовить проект к консольному порту заранее**, пока нет лицензий, чтобы
после покупки dev-доступа порт вставлялся в готовые слоты, а не проектировался с нуля.

> ⚠️ **Без проприетарных SDK.** В репозитории НЕ лежит и не будет лежать ни одного
> файла консольного SDK (хедеры/либы/сэмплы вендора под NDA). Всё ниже — наши
> собственные интерфейсы и заглушки; официальный SDK подставляет **лицензированный
> разработчик** в помеченные точки уже на своей стороне. Так код чист, лежит в репо
> и не тянет юридических рисков.

## 1. Почему порт реалистичен: движок уже backend-agnostic

Игровая логика (`app/`, `game/`, `render/`, `net/`...) общается с ОС **только** через
тонкий слой интерфейсов `src/platform/`:

| Интерфейс | Что абстрагирует | Десктоп-бэкенд |
|-----------|------------------|----------------|
| `Platform.hpp` | init/shutdown, насос событий ОС, курсор, вибро | `platform/sdl/SdlPlatform.cpp` |
| `Window.hpp`   | окно + `NativeWindow` (nwh для bgfx) | SDL |
| `Input.hpp`    | `InputState`: клавиши/мышь/**геймпад**/тач | SDL |
| `FileSystem.hpp` | базовый/пользовательский каталог | SDL |

**Консоль = ещё один бэкенд под теми же интерфейсами.** Игровой код не меняется —
ровно как мы уже сделали для Android (SDL) и планируем для Xbox (нативный WinRT, см.
[xbox-uwp-build-km.md](xbox-uwp-build-km.md)). Это ключ: 90% работы уже сделано тем,
что слой платформы изолирован.

## 2. Что консоли требуют СВЕРХ десктопа

Десктопный `Platform` не покрывает вещи, которые на консоли обязательны для
сертификации. Их выносим в отдельный интерфейс `ConsoleServices` (заглушка на
десктопе — no-op), чтобы игровой код мог их вызывать уже сейчас:

1. **Жизненный цикл**: suspend/resume (сон консоли), constrained-режим (оверлей/скидка
   в фон), запрос выхода — рендер и звук должны корректно вставать на паузу.
2. **Сейвы / storage**: не «файл рядом с exe», а **контейнеры сейвов** через SDK
   (у каждого вендора своё API). Наши `settings/*.cfg`, хотбар, конфиги → в контейнер.
3. **Пользователь / аккаунт**: выбор активного профиля, sign-in, gamer-tag; сеть
   часто требует проверки online-права (entitlement).
4. **Ввод**: только геймпад (+ иногда тач на Switch/портатив). У нас **схема геймпада
   уже спроектирована и реализована** (#115, `docs/gamepad-*`), включая menu-mode
   focus-навигацию — это и есть консольный UX.
5. **Store/цена/иконки**: манифест приложения, возрастной рейтинг, TRC/XR/лоты
   сертификации.

## 3. Разбор по вендорам (точки интеграции SDK)

Общий паттерн один: **свой Platform/Window/Input бэкенд + bgfx с консольным
рендером + ConsoleServices на вендорском API**. Различия:

### Xbox (GDK / Dev Mode)
- Уже расписано отдельно: [xbox-uwp-build-km.md](xbox-uwp-build-km.md). Скелет `uwp/App.cpp`.
- Рендер: **bgfx Direct3D12** (профиль шейдеров `dx11` — уже собираем на Windows).
- Ввод: `Windows.Gaming.Input` (Gamepad) → `InputState`.
- Storage/аккаунт: GDK (XGameSave, XUser). Dev Mode ($19) для проб без девкита.
- Самый дешёвый вход для первого прогона.

### PlayStation 5 (Prospero)
- Рендер: bgfx-бэкенд **AGC/GNM** — **исходники этого бэкенда bgfx отдаёт только под
  NDA** (в публичном bgfx их нет). Подставляется с лицензией.
- Ввод: pad API вендора (DualSense) → `InputState` (у нас уже есть тип `PadType::PlayStation`).
- Storage/аккаунт: save-data + user API вендора → `ConsoleServices`.
- Entry point / main loop: свой, гонит `uaro::Application` (как SDL/WinRT).

### Nintendo Switch (NX)
- Рендер: bgfx-бэкенд **NVN** — тоже под NDA, подставляется с лицензией.
- Ввод: `hid` (Joy-Con/Pro) → `InputState`; на портативе возможен тач (у нас тач-режим
  #114 уже есть).
- Особенность: жёсткие лимиты памяти/производительности → пригодятся наши
  power-preset'ы и render-scale (FSR/SSAA) из видео-настроек.
- Storage/аккаунт: account + fs save-data API вендора → `ConsoleServices`.

## 4. Что уже готово в нашу пользу

- ✅ Изолированный слой платформы (интерфейсы + SDL-бэкенд).
- ✅ **Геймпад-схема и UI** (#115): 7 режимов, панели скиллов, focus-навигация меню,
   magenta focus-ring — полноценный консольный UX без клавиатуры/мыши.
- ✅ **Тач-режим** (#114) — для портативного Switch.
- ✅ Стартовые ассеты (шрифты/переводы/шейдеры/clientinfo) **зашиты в бинарник** —
   на консоли не нужен доступ к файлам для старта UI (важно: у консолей нет «папки
   рядом с exe»).
- ✅ Шейдеры под нужные профили (`dx11` для Xbox D3D12; для PS5/Switch bgfx возьмёт
   свои из консольного бэкенда). Механизм `CLIENT_PREBUILT_SHADERS` уже позволяет
   не зависеть от target-shaderc.
- ✅ Патчер отделяем: на консолях контент кладётся в контейнер/пакет, а не качается
   произвольно — патчер станет опциональным (аналог того, что на UWP GRF в ApplicationData).

## 5. Что делаем СЕЙЧАС (без SDK, чистый код)

1. **`ConsoleServices.hpp`** — интерфейс (lifecycle/save-storage/user) + **десктопная
   no-op реализация**, чтобы `app/`/`game/` могли его вызывать уже сейчас, а консольные
   бэкенды просто заполнили методы. (Инкрементально, не ломая десктоп.)
2. **Слоты бэкендов** `console/<vendor>/` (изолированы от сборки, как `uwp/`): скелет
   Platform/Window/Input бэкенда с TODO-метками «здесь официальный SDK». Никакого
   вендорского кода — только наши интерфейсы-заглушки.
3. **CMake-хуки** под платформенные тулчейны (по образцу arm-кросса: пресет + триплет,
   активируются флагом, по умолчанию не трогают десктоп).
4. **Абстракция storage сейвов**: конфиги/хотбар пишем через `ConsoleServices::save*`,
   на десктопе = текущие файлы, на консоли = контейнер.

## 6. Что ждёт лицензии (нельзя сделать без dev-доступа)

- Реальные SDK-бэкенды (вендорские API ввода/аккаунта/сейвов) в слотах `console/<vendor>/`.
- **Консольный рендер-бэкенд bgfx** (AGC/GNM, NVN) — исходники только под NDA.
- Сборка вендорским тулчейном, подпись пакета.
- Прогон требований сертификации (TRC / XR / Lotcheck) и submission.
