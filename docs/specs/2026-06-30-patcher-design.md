# Патчер uaRO — дизайн

> Статус: согласовано с Sergio 2026-06-30. Реализация на ветке `client/foundation`.

## Назначение

Патчер обновляет файлы клиента **перед входом в игру**. Это не отдельное
приложение, а **фаза внутри самого клиента** (`uaro_client`): при старте клиент
сначала показывает экран патчера (на всё окно), сверяет/докачивает файлы по
манифесту, затем переходит к окну выбора сервера / логину.

## Поток работы

1. Клиент стартует → **фаза патчера** (до логина).
2. Читает `patcher/patcher.cfg` — список URL манифеста `downloads.list`
   (≥2 зеркала, http/https; первый основной, остальные резервные). Если файла
   нет — создаётся с зашитыми по умолчанию адресами:
   - `http://patcher.bornrok.com/downloads.list`
   - `https://patcher.bornrok.com/downloads.list`
3. Тянет `downloads.list` по зеркалам по порядку (первый успешный).
   - **Не удалось ни с одного** → пропускаем патч, сразу к выбору сервера.
   - **Удалось**:
     - совпадает с локальным `patcher/downloads.list` → патч не нужен, к выбору сервера;
     - отличается **или** локального не было → продолжаем (п.4).
4. Локальный `downloads.list` заменяется скачанным (старый удаляется).
5. **Построчная проверка** каждого файла манифеста (см. формат ниже):
   - вычисляем SHA-512 локального файла по целевому пути;
   - совпало с манифестом → следующая строка;
   - не совпало / файла нет → **скачиваем** (см. «Загрузка»).
6. После прохода всех строк → выбор сервера / логин.

> Примечание (подтверждено): если `downloads.list` не изменился, пофайловую
> проверку **пропускаем** (быстрый старт). Локально побитый файл перепроверится
> только когда изменится манифест — это осознанный компромисс.

## Формат `downloads.list`

Текстовая таблица, поля разделены пробелом, по одной записи на строку:

```
<путь-на-сервере>  <SHA512-hex>  <ссылка-зеркала-google-drive>
```

- **Поле 1 — путь/назначение.** Префикс определяет платформу и место в клиенте:
  - `platforms/<platform>/<rel>` — файл только для платформы `<platform>`;
    кладётся в `<root>/<rel>`. Клиент берёт только свои платформенные файлы.
    Пример: `platforms/win-x64/uaro_client.exe` → `<root>/uaro_client.exe`.
  - `root/<rel>` — платформонезависимый файл; кладётся в `<root>/<rel>`.
    Примеры: `root/data.grf` → `<root>/data.grf`; `root/BGM/1.mp3` → `<root>/BGM/1.mp3`.
- **Поле 2** — SHA-512 файла в hex (нижний регистр, 128 символов).
- **Поле 3** — прямая ссылка-зеркало Google Drive (primary-источник).

`<root>` — каталог запущенного клиента; `patcher/` лежит в нём.

## Платформы

Определяются в рантайме (ОС + архитектура процессора, только `x64`/`arm`):

`debian-arm`, `debian-x64`, `fedora-arm`, `fedora-x64`, `sps-x64` (PS4+),
`steamos-x64`, `switch-arm`, `ubuntu-arm`, `ubuntu-x64`, `win-arm`, `win-x64`,
`xbox-x64`, `android-arm`, `android-x64`.

- Архитектура — по compile-time макросам/`uname` (только x64 или arm).
- Linux-дистрибутив — по `/etc/os-release` `ID` (ubuntu/debian/fedora/steamos).
- **Неизвестная платформа** → платформозависимые файлы (`platforms/*`)
  **игнорируются**, применяются только `root/*`.
- Консоли (PS4/Switch/Xbox) — **заглушки** на v1 (закрытая ФС, патч через сторы).

## Загрузка файла

1. **Primary — Google Drive** (поле 3). Подтверждено: GD основной источник,
   особенно для крупных файлов. Реализуется через libcurl с cookie-jar и
   confirm-token (эквивалент curl-цепочки из ТЗ):
   - GET по `uc?export=download&id=<id>` с записью cookies;
   - извлечь `confirm=<token>` из ответа (или из cookie `download_warning`);
   - GET `uc?export=download&confirm=<token>&id=<id>` с теми же cookies → файл.
2. **Fallback — сервер манифеста.** Если с GD не вышло — берём адрес, с которого
   удалось скачать `downloads.list`, и качаем `<server>/<поле1>`.
3. **Атомарность.** Качаем во временный `<target>.part`, по завершении считаем
   SHA-512, сверяем с манифестом; совпало → атомарный `rename` поверх целевого;
   не совпало → удаляем `.part`, помечаем ошибку. Битая докачка не портит установку.
4. Загрузка **последовательная** (по одному файлу).
5. Файлы, **удалённые** из манифеста, локально **не трогаем** (следим только за
   перечисленными).
6. **Не удалось скачать** (ни GD, ни сервер, либо SHA не сошлась) → файл
   **пропускаем** и продолжаем со следующим (патч не прерывается); записываем в
   лог/счётчик ошибок, показываем в UI сводку «N файлов не обновлено».

## Самообновление клиента

Сам `uaro_client` может быть в манифесте (`platforms/<p>/uaro_client[.exe]`).
На Windows нельзя перезаписать **запущенный** exe, поэтому:

1. Скачиваем новый бинарь во временный файл и проверяем SHA-512.
2. **Переименовываем запущенный** `uaro_client.exe` → `uaro_client.old`
   (Windows позволяет переименовать запущенный файл).
3. Кладём новый файл на место `uaro_client.exe` (атомарный rename из `.part`).
4. Просим перезапуск (или перезапускаем сам), пользователь снова входит уже на новом.
5. При следующем старте патчер удаляет оставшийся `uaro_client.old`.

На Linux/Android перезапись допустима и без трюка, но единый путь (rename-then-replace)
оставляем для одинакового поведения.

## Упаковка и загрузка либ — вариант A(1) (решение Sergio)

Цель: **раздавать только `uaro_client.exe`**, который сам докачивает данные и
обновляет себя. Чтобы патчер был самодостаточным и мог обновлять игровые либы
**до** их загрузки:

- **Статически вшиты в exe:** `curl` (нативный TLS — schannel/SecureTransport/…,
  без openssl-DLL), наш `Sha512`, всё ядро/патчер, и **SDL3** (для окна и софт-
  рендера экрана патчера). vcpkg static-триплет (Windows: `x64-windows-static-md`).
- **Delay-load после патча:** `bgfx` и тяжёлый игровой рендер-стек **не
  загружаются** на старте. Патчер работает в фазе «только SDL3», поэтому может
  заменить `bgfx`-DLL на месте (она ещё не загружена). После патча клиент
  инициализирует bgfx (первый вызов → DLL подгружается) и идёт в игру.
  - Windows: `bgfx.dll` помечается `/DELAYLOAD`; не трогаем символы bgfx до конца
    патча. Linux/Android: эквивалент через отложенную инициализацию рендер-модуля.
- Поскольку SDL3 статична, её обновление идёт только через self-update exe
  (rename-self); сам bgfx и контент патчер обновляет напрямую.

Это и «передать только exe» (самодостаточный bootstrap), и «остальные либы
грузятся после патчера».

## UI патчера (фаза до bgfx, на SDL3)

- Отдельная фаза в `Application` **до** инициализации bgfx: открыть окно через
  SDL3, рисовать статус **софт-рендером SDL** (`SDL_Renderer`/поверхность) — bgfx
  здесь недоступен.
- На **всё окно**; фон **светло-голубой**; текст **белый с чёрной обводкой**,
  шрифт **22**. Без новостей. Построчно: «Загрузка `<файл>`… X%», «Проверка
  `<файл>`…», общий прогресс (файл N из M), сводка ошибок.
- `PatchRunner::run` крутится в рабочем потоке; UI читает потокобезопасный
  снимок `PatchProgress` (mutex) и перерисовывает ~30 fps. По завершении —
  инициализируем bgfx и переходим к выбору сервера / `LoginScene`.

## Порядок загрузки приложения (A(1))

1. `main` → создать SDL3-окно (без bgfx).
2. **Фаза патчера** (SDL софт-рендер): рабочий поток гонит `PatchRunner`, экран
   показывает статус. Дождаться завершения.
3. Если был self-update exe — попросить перезапуск (новый exe применится).
4. Иначе: инициализировать **bgfx** на том же окне (delay-load), затем обычный
   старт (`LoginScene`/`MapScene`).

## Архитектура / модули

- `core/crypto/Sha512.{hpp,cpp}` — SHA-512 (вшитая компактная реализация), без зависимостей, юнит-тесты на векторах.
- `patcher/PatchManifest.{hpp,cpp}` — парсер `downloads.list` → записи `{path, sha512, mirror}`, разбор префикса (`platforms/<p>/…` | `root/…`) в `{platform, destRel}`. Юнит-тесты.
- `platform/PlatformId.{hpp,cpp}` — рантайм-детект `<platform>` токена.
- `net/Http.{hpp,cpp}` — обёртка libcurl: GET в память/файл, cookie-jar, прогресс-колбэк; GDrive confirm-flow. (Требует vcpkg `curl`.)
- `game/PatcherScene` (или boot-фаза) — оркестрация + UI; запускается до `LoginScene`.

**curl** добавляется в `vcpkg.json` (`curl` с features http/https; vcpkg собирает из
исходников под триплет). Консольные триплеты — позже.

## Порядок реализации

1. (без GPU/сети, тестируемо) `Sha512` + `PatchManifest` + `PlatformId` + юнит-тесты.
2. `net/Http` (libcurl) + GDrive confirm-flow.
3. `PatcherScene` UI + интеграция в boot до логина.
4. Самообновление (rename-self) + очистка `*.old`.
5. Серверная сторона (генерация `downloads.list`, хостинг) — отдельно, вне клиента.
