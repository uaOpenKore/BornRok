# PNG-спрайты и анимации (#109)

Цель: контент-менеджер добавляет и заменяет спрайты обычными **PNG-файлами**, без
конвертации в форматы Gravity (.spr/.act) и без спец-инструментов. Заодно это открывает
**хай-рез спрайты** (#108 для спрайтов упирался именно в фиксированное разрешение кадров
.spr).

Дизайн из двух уровней — от дешёвого к полному. Уровень 1 покрывает «перерисовать
существующее в хай-резе», уровень 2 — «добавить нового моба/NPC/эффект целиком из PNG».

---

## Уровень 1 — подмена кадров существующего спрайта (хай-рез рескин)

Анимации, якоря и тайминги остаются из родного `.act` — художник заменяет только
картинки кадров.

### Как выкладывать файлы

Рядом с логическим путём спрайта кладётся **папка с суффиксом `.png.d`** и кадрами по
номерам (номер = индекс кадра в `.spr`):

```
data/sprite/몬스터/poring.spr          ← остаётся в GRF, как раньше
data/sprite/몬스터/poring.png.d/       ← loose-папка или в архиве (zip/GRF)
    0.png
    1.png
    ...
    meta.cfg                            ← необязательный
```

- Заменять можно **не все кадры**: кадр без PNG берётся из `.spr` как раньше.
- PNG — любые (8/32 бит, с альфой); прозрачность — обычный альфа-канал PNG
  (никаких «розовых» ключевых цветов).

### Разрешение и масштаб

PNG может быть **в K раз крупнее** кадра `.spr` — целый множитель определяется
автоматически: `K = png.width / spr.width` (проверяем, что и высота кратна, иначе
предупреждение в лог и кадр отклоняется). Логический размер кадра (и вся геометрия
`.act`: смещения слоёв, якоря) остаётся прежним — просто текстура плотнее, как уже
сделано для хай-рез текстур земли/моделей (#108).

`meta.cfg` (опционально, формат как наши .cfg — `ключ значение`):

```
scale 4        # явный множитель, если авто-детект не устраивает
filter linear  # linear|nearest — фильтрация текстуры кадров (по умолчанию из настроек)
```

### Что происходит в клиенте

1. `CharacterActor::loadActor` (и все места, где читается `<base>.spr`) после парса
   спрайта пробует `vfs.read("<base>.png.d/<i>.png")` для каждого кадра `i`.
2. Найденные PNG декодируются (`decodeImage`, PNG уже поддержан) и **замещают пиксели
   кадра** в распакованном RGBA-виде, с запомненным множителем K для загрузки текстуры.
3. Дальше весь конвейер (`composeFrame`, батч, палитры для незаменённых кадров) работает
   без изменений.

Ограничение уровня 1: PNG-кадр — truecolor, значит **красители (.pal, #86) на
заменённые кадры не действуют** (палитра красит только indexed-кадры .spr). Для тела и
волос, где важны палитры-красители, либо не заменять кадры, либо выкладывать по
PNG-папке на каждый цвет (см. уровень 2).

## Уровень 2 — самостоятельный PNG-спрайт (новый контент без .spr/.act)

Полностью новая сущность: папка с кадрами + **манифест анимаций**. Клиент собирает из
неё в памяти обычные `Sprite` + `Action`, так что весь код ниже по конвейеру
(composeFrame, направления, звуковые события) не меняется.

### Раскладка

```
data/pngsprite/<имя>/
    manifest.cfg
    idle_0.png  idle_1.png ...
    walk_0.png ...
```

Имя произвольное; для мобов/NPC оно подключается через таблицу классов так же, как
сейчас маппятся классы → имена .spr (jobname/lua-таблицы).

### manifest.cfg

Тот же стиль cfg (строка = запись, `#` — комментарий):

```
# глобальные
scale 4              # во сколько раз кадры крупнее «логического» размера
directions 1         # 1 или 8 (8 = как у RO: юг=0, по часовой)
anchor 32 60         # опорная точка по умолчанию (пиксели ЛОГИЧЕСКОГО размера,
                     # от левого-верхнего угла кадра; обычно «между ступней»)

# action <имя> <delay-мс-на-кадр>
action idle 150
frame idle_0.png
frame idle_1.png

action walk 90
frame walk_0.png
frame walk_1.png -1 0      # необязательное смещение dx dy кадра
frame walk_2.png

action attack 80
frame atk_0.png
frame atk_1.png sound attack_hit   # звуковое событие на кадре (= ActEvent)
```

- Имена action фиксированы и маппятся на индексы RO (`idle walk sit pick attack hurt
  die attack2 attack3 skill`) — тот же порядок, что в enum `Anim`.
- При `directions 8` каждый action получает 8 вариантов: либо суффиксом файла
  (`walk_S_0.png`, `walk_SW_0.png`, …), либо — если выложен только один — кадры
  используются для всех направлений (для эффектов/иконок этого достаточно).
- Отсутствующий action откатывается на `idle` (как сейчас ведёт себя ACT-плеер при
  отсутствии действия).

### Что происходит в клиенте

Новый модуль `formats/PngSprite` (parse манифеста — чистый core, тестируется офлайн):

1. читает `manifest.cfg`, по нему — все перечисленные PNG через VFS (лист файлов задан
   манифестом явно, листинг директорий VFS не нужен);
2. строит `Sprite` (все кадры RGBA) и `Action` (actions/frames/layers/anchors/events)
   в памяти;
3. отдаёт пару туда же, куда сейчас попадает результат парса `.spr`+`.act`.

Порядок поиска актёра становится: `pngsprite/<имя>/manifest.cfg` → `<base>.spr` +
`<base>.act` (+ подмена кадров уровня 1). Loose-файлы, как и всюду, перекрывают архивы.

## План работ

| Шаг | Объём | Проверяемость офлайн |
|---|---|---|
| 1. `formats/PngSprite`: парс manifest.cfg → `Sprite`+`Action` | ядро | да (unit-тесты в core) |
| 2. Уровень 1: подмена кадров `.png.d/` + множитель K в загрузке текстур | game/render | нет (проверяет Сергио) |
| 3. Уровень 2: подключение в `loadActor` + маппинг классов | game | нет |
| 4. Тест-контент: перерисованный поринг (ур.1) + простой эффект (ур.2) | контент | — |

Вопросы к решению (не блокируют шаги 1–2):
- имя папки/суффикса (`.png.d`, `pngsprite/`) — согласовать с КМ, чтобы удобно паковать;
- нужен ли уровень «PNG-атлас» (один PNG со всеми кадрами + координаты в манифесте) —
  удобнее для больших анимаций, добавим по запросу КМ.
